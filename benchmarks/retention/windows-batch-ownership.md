# Windows batch and fixture retention controls

These experiments investigate [#629](https://github.com/AndrewM-F/bun-native/issues/629). They use the actual React workload and public core against a headless protocol peer on Windows Server 2022, with the pinned Bun, unchanged collection checkpoints and zero-survivor assertion. They do not exercise GPUI, native input, paint or presentation. Failed retention assertions remain failures; the diagnostic job succeeds only when every report is valid and its positive control is observed.

A failure snapshot from [the benchmark run](https://github.com/AndrewM-F/bun-native/actions/runs/45122103683) shows a batch entry's `update` callback retaining a change map, which retains the last content node. The entry itself has no path from a reported root in that snapshot. The listener has a separate lexical-environment owner, also without a complete reported root path. Snapshots are taken after the failed checkpoints and can omit hidden ownership edges; they do not establish the marking source.

[The narrow-scan control](https://github.com/AndrewM-F/bun-native/actions/runs/45125710346) alternated five pairs with `useNarrowReferenceScan` explicitly on and off, verified the effective option dump, and observed a deliberately pinned root in both settings. Development retained indexes 3, 4 and 5 in all ten runs. AOT retained the final content node and listener (298 and 299) in all ten, with one additional index in one enabled-scan run. Disabling that option alone did not remove the failure.

[The batch-release control](https://github.com/AndrewM-F/bun-native/actions/runs/45127583598) built baseline and candidate from the same source except for releasing the batch callback after execution. It alternated five pairs; executable and source hashes are retained in the artifact. Baseline AOT retained indexes 298 and 299 in all five runs. The candidate released index 298 in all five, but retained index 299 in four of five; development retained targets in all ten. The candidate's deliberately pinned-root control was valid. This is a partial ownership reduction, not a complete fix or a performance result.

[The fixture-binding controls](https://github.com/AndrewM-F/bun-native/actions/runs/45130396191) ran three trials per variant on the callback-release candidate. Clearing the fixture's listener variable after disposal released the AOT listener in three of three; clearing the setters did not consistently do so. Clearing both the fixture's view and listener variables yielded zero survivors in all three development and all three AOT trials. Separately pinning the listener or root remained observable. These temporary diagnostic variants are not the shipped fixture and do not identify why its lexical environment survives. No assertion, checkpoint, retry or accepted survivor count was changed.

The retaining root remains unresolved. Further work must distinguish an application or React owner from hidden or conservative runtime roots at the actual collection checkpoint, and qualify any candidate against real native interaction and paired performance before merging it.

The next headless control is predeclared to run three alternating baseline and globally pinned-root trials per execution mode on the callback-release candidate. After the unchanged benchmark checkpoints have failed, it records one additional collection immediately before application shutdown and another after shutdown. The pin must remain visible at all three observations. A target disappearing only after shutdown would warrant further investigation of shutdown-related ownership, but the additional collection itself can change reachability; this control cannot establish causation or turn the original failure into a pass.

In [the shutdown control](https://github.com/AndrewM-F/bun-native/actions/runs/45132076792), every positive control retained the pinned root at all three observations. In all three baseline AOT trials the original checkpoint retained listener 299, and that listener was still observable before and after application shutdown. In all three baseline development trials indexes 3 and 5 survived the original checkpoint but were absent at the additional pre-shutdown observation. Failure-only heap snapshots also perform a collection before those later observations. These findings do not establish a root or explain why AOT and development differ; in particular, disappearance after another collection does not pass the original checkpoint.

The next diagnostic compares three alternating trials per variant with and without dereferencing the probes at the first checkpoint; each variant also has a separately pinned-root positive control. The collection, queue fence, second checkpoint, and failure assertion are preserved. The omitted observation is a diagnostic alteration, so a passing variant would not pass the original benchmark or identify a root by itself. Its purpose is to test whether the first observation affects the second checkpoint.

In [the first-observation control](https://github.com/AndrewM-F/bun-native/actions/runs/45132519273), all three baseline and all three omit-first development trials retained indexes 3 and 5 at the second checkpoint; all corresponding AOT trials retained listener 299. The separately pinned-root variants retained their pinned root in every trial. Skipping the initial dereference alone did not remove the failure in this headless control; it does not identify the retaining root.

## Runtime source provenance for the next trace

The older [root-tracing investigation](root-tracing.md) used Bun `da867c60b` and WebKit `8c6c963e3c49fe39942d9625d1fc924128fad26e`; it is historical evidence, not an observation from this Windows runtime. The Windows benchmark uses Bun `b1007f1177fd402fae67387b8548cae5ae9b5707`, whose [build configuration](https://github.com/oven-sh/bun/blob/b1007f1177fd402fae67387b8548cae5ae9b5707/scripts/build/deps/webkit.ts) pins WebKit `4d45755fed4aeef19e95beb90d3d0c884a2812bd`. An instrumented build must match that newer source and its Windows release configuration before its observations can be compared with the failing workload.

At those two WebKit revisions, `ConservativeRoots.cpp` is byte-identical (SHA-256 `22102e605c012f0134a35c1191f7f4ebb159836fcc8dd078103abcf5de26ff3f`), as is `SlotVisitor.cpp` (`c396ee3e537a59520382a18dea2f4422353b3454684f1a179b94ed3b4a0af79b`). In the newer source, [`JSCellButterfly::visitFields`](https://github.com/oven-sh/WebKit/blob/4d45755fed4aeef19e95beb90d3d0c884a2812bd/Source/JavaScriptCore/runtime/JSCellButterfly.h) still uses hidden value visitation, whereas [`CompactTable::visitEntries`](https://github.com/oven-sh/WebKit/blob/4d45755fed4aeef19e95beb90d3d0c884a2812bd/Source/JavaScriptCore/aot/runtime/AOTCompactTable.h) uses ordinary visitation. These source checks support the tracing plan but are not a new Windows observation and do not identify this failure's retaining root.

Two details constrain a future instrumented build. In the pinned [`SlotVisitorInlines.h`](https://github.com/oven-sh/WebKit/blob/4d45755fed4aeef19e95beb90d3d0c884a2812bd/Source/JavaScriptCore/heap/SlotVisitorInlines.h), hidden visitation returns early for an already marked cell; tracing only `appendHiddenSlow` would therefore miss additional origins. The trace must capture attempted visits before that early return as well as conservative scan origins. Separately, the pinned Bun [`release-local` profile](https://github.com/oven-sh/bun/blob/b1007f1177fd402fae67387b8548cae5ae9b5707/scripts/build/profiles.ts) defaults to LTO off, unlike its release profile. A local-WebKit build cannot be assumed to match the shipped runtime's code generation; record and qualify the actual build flags and compare an uninstrumented build before interpreting any trace.

The pinned [`FastMarkAppender`](https://github.com/oven-sh/WebKit/blob/4d45755fed4aeef19e95beb90d3d0c884a2812bd/Source/JavaScriptCore/heap/FastMarkAppender.h) can also mark through an inline fast path without calling `SlotVisitor::appendHiddenSlow`. In addition, `SlotVisitor::defersRootRegions` treats compiled images differently outside heap analysis. A complete AOT trace must cover these paths and deferred roots as well; logging only the ordinary visitor hooks cannot establish their absence.

The [Windows runner preflight](https://github.com/AndrewM-F/bun-native/actions/runs/45132968582) found approximately 86 GB free, LLVM 20.1.8, no `nasm` on PATH, and Strawberry Perl on PATH. The pinned Bun source specifies LLVM 23.1.1 and its Windows image configuration deliberately uses Git's Perl instead of Strawberry Perl. A source build therefore needs an explicitly provisioned and verified toolchain; the preflight did not build or qualify a runtime.

The next build attempt is an unmodified source baseline using the pinned Bun and WebKit revisions, provisioned LLVM 23.1.1, the pinned Rust nightly and explicit release LTO. A successful build and matching revision are prerequisites only: the resulting binary must still be compared against the pinned distribution on the same Windows workload, including development and AOT positive controls, before it can serve as a tracing reference.

The [first source-build attempt](https://github.com/AndrewM-F/bun-native/actions/runs/45133433335) failed before toolchain provisioning: Windows Git could not create unrelated `LayoutTests` files with long names during the full WebKit checkout. The next attempt excludes that test tree using a sparse source checkout. No runtime was built in the first attempt.

The control driver uses the explicitly selected runtime for bundling, AOT compilation, executable inspection and development execution. Previously its optional runtime argument applied only to development execution, while AOT compilation used `bun` from PATH; that would invalidate a custom-runtime comparison. A local headless wrapper control verified all three build stages used the selected command and that deliberate root pins remained observable in development and AOT. This does not qualify a custom Windows runtime.
