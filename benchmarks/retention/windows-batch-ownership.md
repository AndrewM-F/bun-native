# Windows batch and fixture retention controls

These experiments investigate [#629](https://github.com/AndrewM-F/bun-native/issues/629). They use the actual React workload and public core against a headless protocol peer on Windows Server 2022, with the pinned Bun, unchanged collection checkpoints and zero-survivor assertion. They do not exercise GPUI, native input, paint or presentation. Failed retention assertions remain failures; the diagnostic job succeeds only when every report is valid and its positive control is observed.

A failure snapshot from [the benchmark run](https://github.com/AndrewM-F/bun-native/actions/runs/45122103683) shows a batch entry's `update` callback retaining a change map, which retains the last content node. The entry itself has no path from a reported root in that snapshot. The listener has a separate lexical-environment owner, also without a complete reported root path. Snapshots are taken after the failed checkpoints and can omit hidden ownership edges; they do not establish the marking source.

[The narrow-scan control](https://github.com/AndrewM-F/bun-native/actions/runs/45125710346) alternated five pairs with `useNarrowReferenceScan` explicitly on and off, verified the effective option dump, and observed a deliberately pinned root in both settings. Development retained indexes 3, 4 and 5 in all ten runs. AOT retained the final content node and listener (298 and 299) in all ten, with one additional index in one enabled-scan run. Disabling that option alone did not remove the failure.

[The batch-release control](https://github.com/AndrewM-F/bun-native/actions/runs/45127583598) built baseline and candidate from the same source except for releasing the batch callback after execution. It alternated five pairs; executable and source hashes are retained in the artifact. Baseline AOT retained indexes 298 and 299 in all five runs. The candidate released index 298 in all five, but retained index 299 in four of five; development retained targets in all ten. The candidate's deliberately pinned-root control was valid. This is a partial ownership reduction, not a complete fix or a performance result.

[The fixture-binding controls](https://github.com/AndrewM-F/bun-native/actions/runs/45130396191) ran three trials per variant on the callback-release candidate. Clearing the fixture's listener variable after disposal released the AOT listener in three of three; clearing the setters did not consistently do so. Clearing both the fixture's view and listener variables yielded zero survivors in all three development and all three AOT trials. Separately pinning the listener or root remained observable. These temporary diagnostic variants are not the shipped fixture and do not identify why its lexical environment survives. No assertion, checkpoint, retry or accepted survivor count was changed.

The retaining root remains unresolved. Further work must distinguish an application or React owner from hidden or conservative runtime roots at the actual collection checkpoint, and qualify any candidate against real native interaction and paired performance before merging it.
